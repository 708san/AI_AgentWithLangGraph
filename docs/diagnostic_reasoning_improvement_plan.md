# Zero-shot・暫定診断の改善計画

記録日: 2026-09-15

この文書はユーザーが提示した改善案と運用方針を保持するためのメモです。改善の実装・実行・採用を示すものではありません。

## 対象と目的

担当範囲はLLM Zero-shot推定と暫定診断の改善。正解ラベル付きベンチマークで、各段階の出力とTop-k等の成績を比較する。点数だけでなく、候補・順位・支持理由などの出力のブレも観測する。

## ブランチ運用方針

1. 評価プログラムと改善前評価に関する変更をまとめた統合ブランチを作る。
2. 統合ブランチから、改善案ごとに個別ブランチを作る。
3. 個別ブランチで実装・評価し、改善が認められたものを統合ブランチへマージする。
4. 全改善案の検討後、統合ブランチからmainへのPRを作る。

統合ブランチ: `improvement/llm-pipeline`。評価基盤をコミット・pushした後、改善案ごとに派生ブランチを作る。

評価コード・設定・手順はGit管理し、症例・正解データ・実行出力は既存方針どおり `local_artifacts/` に保持する。改善前の評価結果は上書きせず固定する。統合ブランチへ変更を取り込んだ後も、初期baselineと比較可能にする。

## ユーザーの改善案

### LLM Zero-shot推定

- 禁止事項と実施してほしいことを、プロンプトへより細かく記載する。
- 次の暫定診断もLLMであるため、疾患を推定した理由を保持し、後段の判断材料として渡す。
- 理由付きであるためにLLM候補を過大評価したり、他ツールの結果を過小評価したりしないように注意を促す。

### 暫定診断

- 出力形式を構造化して安定性を改善する。
- 現行の正規表現による解析では、LLMの小さな書式ミスだけで候補が脱落し、精査した情報が失われる可能性がある。
- LLMが扱いやすい出力方式を用いる。
- 情報が失われた場合にログを出し、追跡可能にする。
- 出力結果と入力候補を照合し、安全性を高める。
- `description` が支持理由を書くように指示されている点を見直す。具体的な変更内容は未確定。

## 評価で今後決めること

- 改善の採用基準（Top-k、MRR、候補脱落、出力の安定性など）。
- 繰り返し実行回数と、モデル・プロンプト・検索結果等を固定する範囲。
- Zero-shot理由の保持による効果と、暫定診断の変更による効果を切り分ける実験条件。
- 各改善の単独評価と、統合後の組み合わせ評価の方法。

`scripts/evaluation/` にはZero-shot単体と暫定診断までの実行・出力保存・採点、およびevaluation限定のトレースを実装済み。本番の推論ロジック・Stateは変更しない。

## 現在の優先順位

暫定診断の評価は検索インデックス不足のため一旦後回しにし、Zero-shotから取り組む。

- OMIM欠損と正規化に伴う候補喪失を検討する。ただし、現時点のZero-shot単体評価は正規化を実行しない。確認できた事象は、疾患名が出力されてもOMIMが欠けているとOMIM完全一致採点ではヒットしないこと。正規化による喪失は別途検証する。
- 構造化出力のOMIM欄に説明・ID例・欠損時の表現を設ける改善を検討する。例の欠如が型崩れの原因という点は仮説であり、文字列 `"null"` と実際のnull、ID書式の妥当性を分けて評価する。
- Zero-shotプロンプトを改善し、同じベンチマーク・反復条件で精度と出力の安定性を比較する。

評価環境はPython 3.12へ移行済み。既存のZero-shot評価はPython 3.9で取得したため、改善前後の比較時にはPythonを含む実行条件も揃える。
